# B2 存储运维文档（v4.4.0）

> 配套「追光学科共享平台」文件存储迁移至 Backblaze B2 私有桶。
> 阅读对象：超管 / 运维。普通用户无需阅读。

---

## 一、架构现状

```
浏览器 → Cloudflare Worker(worker-api.ts) → Backblaze B2 私有桶(zhuiguang-k12-004)
            ↑ 全部上传/下载/鉴权代理都走这里，浏览器永不直连 B2
D1(file_meta 等表) = 文件元数据唯一来源（不调 B2 List，不运行时校验存在）
```

- **桶**：`zhuiguang-k12-004`（allPrivate 私有桶）
- **后端模式**：`B2_FREE`（默认，不绑卡，0 元/年，目标 10GB）
- **切换**：环境变量 `STORAGE_MODE` = `B2_FREE` / `B2_PAID` / `SUPABASE`，可一键回滚。代码永不自动切付费。

## 二、已知限制（务必知悉）

1. **下载速度取决于 CF 缓存命中率**。缓存命中 = CF 边缘节点直接返回（通常 < 100ms）；未命中 = 回源 B2 美国西部源站（跨太平洋，单文件常需 1~3s）。这是**物理距离**决定的，**无法彻底消除，只能靠缓存缓解**。
   - v4.4.1 优化：鉴权落 D1（省 200~600ms）、统计落库异步化（省 60~150ms）、私有文件也给 300s 边缘短缓存。
   - **运维手段**：管理后台 → 运行监控 → B2 存储 → 「预热 TOP10 文件」，把高频文件推进边缘缓存。
2. **B2 免费账户会随机出现 429 限流**（与配额无关），表现为偶发上传/下载失败。重试即可。
3. **B2 免费模式当日 B 类读请求打满 2500**：已缓存旧文件正常访问；**新回源会被阻断，UTC 零点自动恢复**。
4. **D1 写满会让整个站点全部业务瘫痪**（不只是文件功能），需定期关注 D1 用量。
5. **官方配额字段在本账户不可用**：见第三节。
6. **B2 桶已用容量无法从「桶摘要」拿到**：`b2_list_buckets` 响应**不含** `fileCount` / `totalSize`（v4.4.0 曾误以为有）。只能通过 `b2_list_file_names` 全量盘点求和（属 Class A）→ 因此**每日限 1 次**并落库 `b2_bucket_census`。
7. **⚠️ 盘点求和必须用 `contentLength` 字段，不是 `size`**：`b2_list_file_names` 响应中文件大小字段名为 `contentLength`（v2/v3 实测一致，`size` 恒为 `undefined`）。写成 `f.size` 会**静默算出 0 字节**——面板显示「已用 0 B」但文件实际都在，极难排查。正确写法：`Number(f.contentLength ?? f.size ?? 0)`。
   - 该 bug 曾让 `b2_bucket_census` 落库错误值（16 文件 / 0 字节），已于 v4.4.1 修复并重跑盘点覆盖为 **16 文件 / 5,378,780 字节（5.13 MB）**。
   - **排查口诀**：容量显示 0 但文件能正常下载 → 99% 是字段名问题，不是文件丢了。

## 三、配额统计说明（重要）

需求要求「配额从 B2 官方拉取」。以下为 **v4.4.1 实测结论，请勿重复试错**：

| 想拿的官方数据 | 途径 | 实测结果 |
| --- | --- | --- |
| 当日 B 类交易数 | 下载响应头 `b2-api-b-class-transaction-count-today` | ❌ **不返回**（CDN GET 与 `b2_download_file_by_id` 两种方式均 `null`） |
| 账户容量 / 是否超限 | `b2_get_account_info` | ❌ **v2 / v3 均 404 not_found**（主密钥 capabilities 为空；B2 的 application key 也**不提供** `readAccountInfo` 选项） |
| 桶已用容量 / 文件数 | `b2_list_buckets` | ⚠️ 可用，但响应**不含** `fileCount` / `totalSize` 字段 |
| 桶已用容量 / 文件数 | `b2_list_file_names` 全量枚举求和 | ✅ **唯一可用途径**，属 **Class A**（免费 2500/日）→ 每日限 1 次 |
| 容量上限 10 GB | API | ❌ 取不到 → 用 B2 公开免费档位**常量**，面板标注「以 B2 控制台 Billing 页为准」 |

**处理方式**：

- 「当日回源次数」仍是**本系统真实回源计数**（每真实回源一次 +1，非估算、非猜测），
  面板**明确标注「本地统计·非官方」**，绝不冒充 B2 官方数字。软上限/告警基于它兜底。
- 「官方已用容量」改为**每日 1 次真实盘点**落库 `b2_bucket_census`，面板显示盘点日期与「今日/非今日」标签。

> 若未来升级为可拿官方配额的 B2 账户/密钥，可在 `storage-layer.ts` 的 `serveFileById` 第6步
> 改为读取官方头并 upsert，无需改表结构。

## 三·补：C 类交易治理（v4.4.1 修复的线上问题）

**现象**：只下载了 1 个文件，B2 控制台「Class C transactions today」却显示 8 次。

**原因**（B2 交易分类）：

- `b2_authorize_account`（鉴权）→ **Class C**
- `b2_list_buckets` / `b2_get_bucket_info` / `b2_get_account_info` → **Class C**
- 免费账户 Class C 上限 **2500/日**（与 A、B 类额度各自独立）

两个叠加的浪费点：

1. token 只存在 Worker **模块级变量**里。Cloudflare 在全球多个 PoP 各起一个 isolate，
   且 isolate 空闲后会被回收（冷启动）—— 每个 isolate 首次请求、每次冷启动都要重新鉴权 1 次 C 类。
2. v4.4.0 的监控面板每次刷新都调 `b2_list_buckets`（C 类）。刷 8 次面板 = 8 次 C 类。

**修复后**：

- 新增 D1 表 `b2_auth_cache`（单行）：token 落库，**全球 isolate 共享** → 正常每日仅 1 次 C 类。
  三级缓存：进程内内存 → D1 → 真调 B2；并发请求用 in-flight Promise 合并。
- 监控面板改为**只读 D1 快照**，刷新不消耗任何 B2 交易。
- 删除已确认 404 的 `b2GetAccountInfo()`；上传 URL 也缓存复用（B 类）。

**运维提示**：仍发现 C 类异常增长时，先查是否刚做过 `wrangler deploy`（新版本 = 全部 isolate 重建 = 重新鉴权），
这属正常，每日 1~2 次可接受。

## 四、禁止事项

- 🚫 **禁止直接登录 B2 后台手动增删改文件**。所有文件操作必须经 Worker，否则 D1 元数据与 B2 对象会不一致，导致文件"存在却打不开"或"已删却还能下"。
- 🚫 禁止在下载链路加同步重型计算 / 二次复制文件流。
- 🚫 后端 Worker **不做任何图片处理**（不转码、不压缩），图片 WebP 转码只在浏览器前端执行。
- 🚫 禁止原地覆盖文件：更新必生成新 fileId。

---

## 五、备份要求

- B2 桶本身有版本/生命周期，但**本系统不依赖 B2 版本做回滚**。重要教学资料上传后，建议超管定期通过 B2 控制台或 `rclone`/`b2` CLI 做桶级备份到异地。
- 迁移前请确保 Supabase 上的旧文件**未被删除**（迁移是"复制"而非"移动"，旧文件保留作兜底）。

## 六、监控面板怎么看（管理后台 → 运行监控）

v4.4.1 起有两个 B2 相关 tab（原「Supabase 存储」「Supabase 数据库」已废弃下线）：

### 「B2 存储」tab

- **容量进度条**：已用 / 10GB，附「立即盘点」与「强制重扫」按钮；显示盘点日期 + 今日/非今日标签。
- **B2 存储概况**：后端模式、桶名、桶类型、文件总数、剩余空间。
- **今日回源**：标注「本地统计·非官方」，含告警阈值与耗尽状态。
- **下载性能**：缓存命中率、命中/回源次数、命中耗时 vs 回源耗时 + 「预热 TOP10 文件」按钮。
- **今日流量**：上传数/流量、WebP 转换统计。
- **存量迁移（Supabase → B2）**：已迁文件数/体积 + 「全量迁移」「仅盘点」按钮。
- **大体积文件 TOP 10**：按体积排序，可预览/下载/删除；「仅看未关联」筛出疑似残留。

### 「B2 交易与配额」tab

- A / B / C 三类交易说明与免费额度。
- **C 类异常消耗的原理与修复说明**（见「三·补」）。
- 用户回源 TOP、缓存分布、Supabase 废弃状态。

### 「存储优化」tab（B2 专用）

- 后端模式、D1 元数据文件数、WebP 统计、回源进度条、缓存命中率、回源 TOP、快捷操作。

> 监控仅页面内告警，**无邮件/推送**。超管需**定期主动查看**。
> 回源逼近上限或命中率偏低时面板会输出告警，处理方案：预热高频文件、清理冷文件、调大缓存 TTL。

## 七、人工测试校验清单（上线后必做）

1. 新上传图片强制输出 WebP，画质无损（对比原图文字清晰）。
2. PDF / Word / Excel / PPT **完全不被转码篡改**（二进制一致，可 diff）。
3. 历史存量图片迁移后维持原格式，不自动转 WebP。
4. B2 回源统计 / 告警 / 降级功能校验。
5. 文件下载流式转发：大文件（>10MB）不会占满 Worker 内存；缓存命中下载速度明显优于回源。

## 八、故障行为速查

| 现象 | 原因 | 处理 |
|---|---|---|
| 新文件当日无法下载，旧文件正常 | 免费额度 B 类打满 2500 | 等 UTC 零点恢复；或清理冷文件降回源 |
| 偶发上传/下载失败 | B2 免费账户随机 429 | 前端重试即可 |
| 首次下载慢、刷新后快 | 缓存未命中→回源海外 | 正常；可对热门文件用预热接口 |
| 整站瘫痪 | D1 写满 | 紧急清理 D1 / 扩容 |
| 监控「B2 回源统计」标注"非官方" | 本账户无官方配额字段 | 正常，属方案3设计 |

## 九、常用运维命令

```bash
# 部署 Worker（需在本机，有 CF 凭证）
CLOUDFLARE_API_TOKEN=xxx npx wrangler deploy

# D1 建表（首次）
npx wrangler d1 execute zhuiguang-db --remote --file=migrations/0001_b2_storage.sql

# 存量迁移 Supabase→B2（超管调用，分批）
curl -X POST https://<你的worker域名>/api/admin/migrate/to-b2 \
  -H "Authorization: Bearer <超管token>" \
  -H "Content-Type: application/json" \
  -d '{"limit":50}'
# 重复调用直至 done+failed+skipped 覆盖全部 total

# 预热热门文件（超管）
curl -X POST https://<你的worker域名>/api/admin/prewarm \
  -H "Authorization: Bearer <超管token>" \
  -H "Content-Type: application/json" \
  -d '{"fileIds":["abc123","def456"]}'
```
